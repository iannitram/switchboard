## The question

For each of the five stores: lock, or leave. The facts point to this proposal, to confirm or correct:

- **SnapshotStore: lock.** It is the only one of the five that two processes write at once today with a read before the write. Every write of a repo's snapshot file holds that file's lock: the three read-change-write sites and the plain save. The wait is 10 s, as `waiting::LOCAL_LOCK_WAIT` and `thread::THREAD_LOCK_WAIT`. Reads take no lock.
- **StateStore: lock when the runner gets a face**, not before. Nothing outside tests makes one today.
- **Settings, AutopilotState, Repo backup manifest: leave.** Each has one writer at a time already, for the reasons in the table.

The ruling also settles the GLOSSARY wording. The "State file" entry, added by {{#f-module}} word for word from the owner ruling, reads "A JSON file Switchboard owns and rewrites whole under a lock." Five of the nine State files take no lock today, and under the proposal above four still take none of their own. So for the entry, pick one:

- (a) **Reword it** to match the stores. Proposed: "A JSON file Switchboard owns and rewrites whole; a store that two processes change takes a lock for the change."
- (b) **Keep it** as the rule to reach, and lock every store that is left.

Proposed: (a).

**Why the plain save must hold the lock too:** if only the three read-change-write sites held it, a fresh save from another process could still land between such a site's read and its write, and be overwritten. With every write under the lock, the fresh save waits and lands last.

If the ruling locks the `SnapshotStore`, the snapshot clause no longer states the whole rule, and this issue's PR revises that one clause, as {{#s-musts}} left it, to say a snapshot is written under its file's lock.
